# Real-Model End-to-End Benchmark Contract

**Status: specified, not yet run.** This document is written *before* any model
access so the design cannot be tuned after seeing a number. Any deviation made
later must be recorded here with its reason.

## What this measures, and why it is the only gap left

Every existing measurement in this repository uses subprocesses burning SHA-256.
They establish scheduler *behaviour* — preemption removes ~94% of doomed
compute, critical-path ordering wins ~1.19x — but the project's actual claim is
about long-horizon **Agent** efficiency:

> Reach the same verifiably-correct Goal for fewer tokens by not doing work that
> is already void.

No token has ever been measured. Until one is, that claim has no evidence of the
right *kind*, and no amount of further systems optimisation supplies it.

## Primary hypothesis, pre-registered

> When an upstream artifact changes mid-run, LongHorizonOS reaches the same
> VERIFIED Goal using **fewer total model tokens** than checkpoint/resume,
> because it re-executes only the invalidated cone instead of continuing from a
> position whose validity it cannot assess.

**Null result is a publishable outcome.** If token cost is equal or worse, this
document records that, and the reason.

## Why the verifier must not be a model

Task success is decided by **`pytest` on the generated code** — never by an LLM
judge. Two reasons, both fatal if ignored:

* a model judge makes "both arms reached the same VERIFIED Goal" unprovable,
  because the judgement itself varies per call;
* it would let the measurement inherit the model's bias, so a token saving could
  come from the verifier getting laxer rather than from less waste.

Evidence therefore binds to an exact test outcome over an exact file version.

## Workload

A small Python package generated by the model from a written spec. Deliberately
the same *shape* as `lhos.benchmarks.scheduling_regimes`, so the deterministic
benchmark remains the control for this one.

```text
core.py                 shared API, the thing that changes
├── group A  (depends on core)      3 modules, each with a fixed test
└── group B  (independent of core)  3 modules, each with a fixed test
```

* **Two independent groups on purpose.** A single shared root would invalidate
  everything on any change, making *preserved* work unmeasurable — the preserved
  count would always be zero. This trap already cost one benchmark in this repo.
* **Tests are fixed and written by hand, not by the model.** The model implements
  against them; it never authors its own success criterion.
* ~8 tasks total: `core`, 3× group A, 3× group B, one integration task.

### The mid-run change

After the Goal first closes, **`core.py`'s API signature changes** (one function
gains a required parameter). Ground truth is therefore known exactly:

* group A modules and the integration task **must** be redone;
* group B modules **must not** be redone;
* the new `core` contract must be verified by its own test.

This is machine-checkable, so over- and under-invalidation are both detectable.

## Arms

Equal resources everywhere: same model, same temperature, same agent count, same
per-task retry ceiling. Only the reaction to change differs.

| Arm | Behaviour on change |
|---|---|
| `restart` | discard all state, rebuild every task from scratch — the floor |
| `resume` | keep every prior result, continue from the stopped position, redo only what fails a test afterwards — **the realistic competitor** |
| `lhos` | version-aware invalidation: redo exactly the STALE cone, preserve the rest |

`resume` is the honest opponent. A checkpoint knows *where* execution stopped;
the claim is specifically that this is not enough, because it preserves position
rather than validity. `restart` is included only to bound the range.

## Metrics

**Primary**

1. `total_tokens` (prompt + completion) to reach verified closure, before and
   after the change.
2. `doomed_tokens` — tokens spent on attempts whose declared input was
   superseded before they committed. Attributable, not inferred.

**Structural, deterministic — the explanatory backbone**

3. `tasks_reexecuted_after_change` and `tasks_preserved`.
4. `over_invalidation` / `under_invalidation` against the known ground truth.

These matter more than they look. With a real model the same task may take one
attempt or three at random, so **model variance can dwarf the scheduling
effect**. The structural counts do not vary with sampling, so they explain a
token difference instead of merely restating it — the role `chain_priority`
plays for wall-clock in the deterministic benchmarks.

**Secondary**

5. Wall-clock, model calls, latency. Reported, never used as the headline.

**Correctness gates — a violation voids the run**

6. All arms reach an identical VERIFIED task set.
7. Zero false VERIFIED: every Evidence record must correspond to a passing test
   over the exact committed file version.
8. Zero under-invalidation: a preserved task whose test fails after the change
   is a correctness failure, not a saving.

## Method, fixed in advance

* **n = 5 complete runs per arm**, reporting median/min/max. A single run is not
  reportable: model sampling noise here is worse than the ±20% wall-clock spread
  already measured on the deterministic workloads.
* **Alternating arm order** across repetitions, so a warm cache or a rate-limit
  ramp cannot pose as a win.
* **A separate freshly-generated workspace per arm.** A shared one previously
  let the first arm pay CPython bytecode compilation and inflated a result to a
  fake 2.48x.
* **temperature 0**, fixed seed where the provider supports it. Whether the
  provider actually honoured it is recorded, not assumed.
* **Hard spend ceiling per run**, fail-closed: a run that exceeds its token
  budget is aborted and reported as aborted, never truncated into a result.
* Raw per-call records (model, task, tokens, latency, outcome) are archived to
  `artifacts/` so the aggregate can be recomputed.

### Estimated cost

~8 tasks x ~2–5k tokens per attempt x ~1.5 attempts ≈ **30–60k tokens per run**;
3 arms x 5 repetitions ≈ **0.5–1M tokens** for the full matrix. A single
smoke run (1 arm, n=1) is ~50k and should be done first to validate plumbing
before spending the rest.

## Threats to validity, stated up front

* **Model variance may exceed the effect.** Mitigated by n=5 and by the
  structural metrics; if the token intervals overlap, the honest report is "not
  resolvable at this sample size", not a directional claim.
* **Generated workload, not a real repository.** This measures reaction to a
  known change on a controlled graph. It does not establish behaviour on
  arbitrary human codebases.
* **Single provider, single model.** No claim transfers to other models.
* **The 10h → 3h aspiration is out of scope here.** This measures token cost on
  an 8-task graph, not a ten-hour session.
* **`resume` is implemented by us**, so it could be made artificially weak. Its
  implementation is therefore constrained to: keep all prior artifacts, re-run
  every test, redo only failures. No cheating in either direction.

## Implementation notes

Partly built. Two distinct layers, and only the first exists:

**Layer 1 — transport and token accounting (done).**

* `src/lhos/benchmarks/semantic_repair/live_model.py` — OpenAI-compatible chat
  client, multi-key rotation, per-call token/latency records, secret redaction in
  errors.
* Endpoint and model are environment-settable, so no key or URL ever needs to go
  into a tracked file:
  `LHOS_LIVE_BASE_URL`, `LHOS_LIVE_MODEL`, `STEPCODE_API_KEY`
  (or `STEPCODE_API_KEYS` for a comma-separated rotation set).

**Layer 2 — the scenario in this document (NOT built).**

The existing probe sends a trivial prompt (*"reply with exactly PASS"*) and
multiplies the observed per-call cost by the attempt counts the scheduler
produced. That is a **proxy metric, not this contract**: token cost there is by
construction proportional to attempt count, which the deterministic benchmarks
already measure, so it cannot independently support the hypothesis. What is
missing is the part where the model actually writes the package and `pytest`
decides the outcome.

Do not report Layer 1 output as evidence for the primary hypothesis.

## Running it

Layer 1 smoke, to prove credentials and token accounting are live (a few hundred
tokens):

```bash
export LHOS_LIVE_BASE_URL=https://api.deepseek.com
export LHOS_LIVE_MODEL=deepseek-chat
export STEPCODE_API_KEY=...            # never commit; never paste into a chat
lhos benchmark semantic-repair --quick --live-model --json
```

Expect `live_model.json` in the summary directory with non-zero
`usage_reported` totals. A zero total means the provider did not return usage and
the token metric is unavailable rather than zero.

### Credential note

The credential must be exercised from the machine that will run the benchmark.
During specification, a working key failed from a sandboxed egress
(`401 invalid`) while succeeding from the developer's own host, with the provider
echoing the correct key suffix — so the request arrived intact and was rejected
on origin, most likely an IP restriction. Run the live arms locally rather than
forwarding credentials.
